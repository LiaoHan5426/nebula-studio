# Nebula Studio 全局体验基线

> 基线日期：2026-07-26
>
> 适用范围：Shell、Integration、Settings、Login、Docs，以及 Web/Electron 宿主

## 1. 目的

本文是 Phase 2 的实现基线，用于约束后续页面开发。它不替代用户研究；角色任务来自当前路由、权限与业务流程走查，必须在首次资源门户纵向切片前由产品负责人和真实用户校准。

可交互的组件状态样例位于 Docs：

```text
/patterns/experience-baseline
```

## 2. 应用与页面清单

| 应用面 | 代码入口 | 当前主要页面 | 主要角色 | Phase 2 结论 |
| --- | --- | --- | --- | --- |
| Shell | `apps/web/src/workspace` | 侧栏、标签、应用坞、iframe、通知、组织切换 | 所有登录用户 | `shell` surface，紧凑密度 |
| Integration Portal | `apps/sub-web/integration` | 库表订阅、我的服务 | 资源消费者 | `portal` surface，舒适密度 |
| Integration Provider | 同上 | 数据源、服务注册/发布、Flow、DAG、任务、治理 | 资源提供方 | `provider` surface，紧凑密度 |
| Integration Admin | 同上 | 插件、租户、审批、Executor、日志、拓扑 | 平台管理员 | `admin` surface，紧凑密度 |
| Settings | `apps/sub-web/settings` | 用户、角色、权限、组织、应用、日志、外观、配置 | 用户/组织管理员/平台管理员 | `settings` surface，紧凑密度 |
| Login | `apps/web/src/auth` + `packages/platform/login-ui` | 账号登录、组织选择 | 未登录用户 | `auth` surface，舒适密度 |

## 3. 角色与任务假设

| 角色 | 高频任务 | 需要避免 |
| --- | --- | --- |
| 资源消费者 | 查找资源、比较、申请、查看进度、获得接入信息 | 暴露发布、PF4J、Executor 等治理术语 |
| 资源提供方 | 创建和发布资源、管理版本、处理授权、查看运行摘要 | 与平台级租户、插件安装权限混淆 |
| 组织管理员 | 管理成员、角色、组织策略和组织范围审批 | 看到平台全局配置和无关租户 |
| 平台管理员 | 管理插件、租户、策略、路由、配置和审计 | 在门户中混入高风险治理动作 |
| 开发者 | 查组件/API、复制示例、确认可访问性和响应式行为 | 产品帮助与组件参考混排 |

待校准问题：

1. 消费者最常查找的资源类型和筛选维度是什么？
2. 申请资源时哪些信息必填，哪些可以从组织上下文自动推导？
3. 提供方和组织管理员是否由同一批用户承担？
4. Shell 首页最有价值的三个摘要是什么？
5. 普通用户是否需要直接访问组件文档，还是只访问产品帮助？

## 4. Surface 与密度契约

每个页面必须具有：

```ts
{
  title: string
  surface: 'auth' | 'shell' | 'portal' | 'provider' | 'admin' | 'settings' | 'docs'
  density: 'comfortable' | 'compact'
  helpKey: string
  roles?: string[]
  keywords?: string[]
  returnTo?: string
}
```

- `comfortable`：资源发现、登录、文档和阅读型详情。
- `compact`：Shell chrome、提供方工作台、管理后台和 Settings。
- 页面不得根据 URL 字符串推断 surface。
- 业务页面不得重新声明内容宽度、标题间距、状态色和焦点环。

## 5. 内容与交互规范

### 5.1 术语

- 使用“资源门户”，不使用“应用工作台”指代资源消费界面。
- 使用“提供方工作台”，不使用“我的管理中心”。
- 使用“平台管理中心”，只面向平台管理员。
- 使用“审计日志”，不使用含义过宽的“日志管理”。
- 中文界面使用中文动作词；API、DAG、SLA、Connector 等专业缩写保留英文。

### 5.2 状态

所有数据区必须处理：

1. loading：保持结构稳定，说明正在加载什么；
2. empty：说明为什么为空，并提供下一步；
3. error：保留用户输入，提供重试或帮助；
4. partial-data：说明哪些内容不可用；
5. restricted：说明权限范围和申请/返回路径；
6. disabled：解释不能操作的原因。

状态不能只通过颜色表达。当前步骤使用 `aria-current="step"`，错误使用 `role="alert"`，动态结果使用 `role="status"`。

### 5.3 图标与动作

- 使用 `NebulaIcon` 和本地 Lucide 集合，不使用“服、插、租、×、⌕”等文字充当图标。
- 只有图标的按钮必须提供 `aria-label`。
- 危险操作使用明确动词和影响对象，例如“删除用户 张三”，不只写“确认”。
- 主动作每个区域最多一个；次要动作使用 outline/secondary/ghost。

## 7. 响应式与可访问性基线

| 宽度    | 期望                                                |
| ------- | --------------------------------------------------- |
| 320 px  | 单列；导航可折叠或置顶；主动作不溢出                |
| 768 px  | 可使用双栏；筛选和动作允许换行                      |
| 1280 px | 标准桌面布局                                        |
| 1440 px | 内容遵循 reading/standard/wide 最大宽度，不无限拉伸 |

- 所有页面必须有一个可识别的主标题。
- landmark 顺序为导航 → header → main。
- 键盘焦点可见；浮层关闭后焦点返回触发元素。
- 支持 `prefers-reduced-motion`。
- 正文和控件目标为 WCAG 2.2 AA。

## 8. 验收与后续

Phase 2 自动化基线：

- UI 模式语义单元测试；
- Integration 路由体验元数据完整性测试；
- Docs 体验模式页在多状态间可交互；
- Playwright 检查六类界面的 surface、关键 landmark、横向溢出和键盘焦点；
- `e2e/experience-baseline.spec.ts-snapshots` 保存六类界面在亮色/暗色和 320/768/1280/1440 px 下的 48 张基准截图。

用户访谈、任务优先级和文案确认尚需产品参与。在这些输入完成前，可以实现公共骨架，但不得将推荐资源、审批字段和权限模型视为已验证需求。
